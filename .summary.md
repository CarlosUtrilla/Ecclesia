## Goal
- Fix schedule UI labels and items-on-live content not updating when songs/media/presentations are saved.

## Done
- **Fixed `liveContext.tsx` syntax error**: Extra `})` from the removed `.then()` block was causing a parse error.
- **Label reactivity (`scheduleItem.tsx`)**: Replaced `useEffect`+`getScheduleItemLabel()` async pattern with direct `useMemo` that derives labels from `songs`/`media`/`presentations` context arrays. Added single-mount fallback fetch for items not yet in those arrays.
- **Label reactivity (`LibraryItemPreview.tsx`)**: Same pattern change — `useMemo` replacing `useEffect`+`getScheduleItemLabel()`.
- **Context exposure**: Added `presentations` array to `useIndexDataItems` return, `ScheduleContext` value, and `IScheduleContext` type.
- **Live broadcast label reactivity (`liveContext.tsx`)**: Added `itemOnLiveLabel` memo deriving label from `songs`/`media`/`presentations`. Replaced `getScheduleItemLabel` promise in `liveStateUpdate` effect → no more stale labels.
- **Root cause — `liveItemContent` query never invalidated**: `items-on-live/index.tsx` has a local `useQuery({ queryKey: ['liveItemContent', ...], queryFn: () => getScheduleItemContentScreen(...) })`. This query key only changes when `itemOnLive.accessData`, `liveContentVersion`, or `presentationBibleOverrideByKey` change — NOT when songs/media/presentations are refetched. Added `queryClient.invalidateQueries({ queryKey: ['liveItemContent'] })` in `main.tsx` alongside the existing `songsByIds`/`mediaByIds`/`presentationsByIds` refetch logic. Now when a song is saved, the `liveItemContent` query is invalidated and re-fetches with fresh data.

## Key Insights
- **Schedule UI labels** update via `useMemo` → `songs`/`media`/`presentations` context arrays → React Query refetch → context value change → re-render.
- **Items-on-live content** updates via `liveItemContent` query invalidation → fresh `getScheduleItemContentScreen()` call with updated arrays.
- The `liveContext.tsx` contentScreen effect `[getScheduleItemContentScreen, itemOnLive, presentationBibleOverrideByKey]` was never the bottleneck — it DOES re-run when `getScheduleItemContentScreen` reference changes. But the items-on-live LOCAL query (`liveItemContent`) bypassed this effect entirely and didn't know about data changes.
